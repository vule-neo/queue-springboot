2. Arhitektura: modularni monolit

Jedan deployable proces, ali podijeljen u pakete kao da su zasebni servisi. Paketi: organizations, locations, servicetypes, queues, tickets, users, notifications, analytics, common, config.

Zašto ne mikroservisi? Mikroservisi rješavaju probleme koje ovaj sistem nema (nezavisno skaliranje timova i dijelova, različiti jezici, izolacija deploya), a donose probleme koje bi bili stvarni: distribuirane transakcije, mrežne greške, pet repozitorija, pet pipelinea. Monolit s čistim granicama se može rascijepiti kad zatreba; mikroservisi napravljeni prerano se teško spajaju nazad. Ovo je i standardni odgovor na intervjuu: „počeo sam monolitom s modularnim granicama, jer je to jeftinije mijenjati".

Dio II — Slojevi

4. Baza podataka i Flyway

Kako Flyway radi

SQL fajlovi u src/main/resources/db/migration, imenovani V1__init.sql, V2__users.sql, V3__events.sql, V4__ticket_user.sql. Pri startu Flyway pogleda svoju tabelu flyway_schema_history, vidi koje su migracije već izvršene, i pusti samo nove — redom po verziji. Svaka se izvrši tačno jednom i pamti se njen checksum: ako naknadno promijeniš već izvršenu migraciju, Flyway odbije da starta.

Pravilo koje se krši i skupo plaća: izvršena migracija se nikad ne mijenja. Greška se ispravlja novom migracijom. Razlog: na tvom laptopu bi se promjena „primila" tek poslije brisanja baze, a u produkciji nikad.

Ključni dio šeme

CREATE TABLE ticket (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    queue_id     BIGINT      NOT NULL,
    number       VARCHAR(10) NOT NULL,     -- "A007", ono što čovjek vidi
    sequence_no  INT         NOT NULL,     -- redni broj u danu, za sortiranje
    issued_date  DATE        NOT NULL,
    status       VARCHAR(20) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    called_at    TIMESTAMPTZ,              -- null dok se ne desi
    completed_at TIMESTAMPTZ,
    user_id      BIGINT,                   -- V4: ko je uzeo broj (nullable)

    CONSTRAINT fk_ticket_queue FOREIGN KEY (queue_id) REFERENCES queue (id),
    CONSTRAINT uq_ticket_queue_date_seq UNIQUE (queue_id, issued_date, sequence_no),
    CONSTRAINT ck_ticket_status CHECK (status IN (
        'WAITING','CALLED','SERVING','COMPLETED','CANCELLED','NO_SHOW','SKIPPED'))
);

Tri stvari vrijedne pažnje:

  • uq_ticket_queue_date_seq — jedinstven redni broj po redu i danu. Ovo je posljednja odbrana od race conditiona: čak i da lock zakaže, baza ne dozvoli dva ista broja.
  • ck_ticket_status — baza ne vjeruje aplikaciji. Ako neko upiše status koji ne postoji u enumu, insert pada.
  • TIMESTAMPTZ, ne TIMESTAMP — čuva trenutak u UTC-u s poznatom zonom. TIMESTAMP bez zone je „14:00 negdje" i pravi bugove pri promjeni vremena i pri serverima u drugoj zoni.

Konfiguracija koja to čuva

spring.jpa.hibernate.ddl-auto=validate   # Hibernate SMIJE samo provjeriti, nikad mijenjati
spring.jpa.open-in-view=false            # lazy loading van transakcije puca ODMAH
spring.flyway.enabled=true
open-in-view=false je važan detalj. Spring Boot ga podrazumijevano drži na true: transakcija ostaje otvorena do kraja HTTP odgovora, pa lazy kolekcije rade „magično" i u kontroleru. Posljedica je N+1 problem koji niko ne primijeti dok baza ne počne da gori. Sa false, pristup lazy polju van servisa baca LazyInitializationException — greška odmah, umjesto sporosti kasnije.

5. Entiteti i JPA/Hibernate

@Entity
@Table(name = "ticket")
@Getter @Setter @NoArgsConstructor
public class Ticket {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "queue_id", nullable = false)

    @Column(nullable = false, length = 20)
    private TicketStatus status;

    @CreationTimestamp
    @Column(name = "created_at", nullable = false, updatable = false)

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")

Odluke

OdlukaZašto
@Enumerated(EnumType.STRING)Default je ORDINAL — upisuje redni broj konstante. Ako neko ubaci novu konstantu u sredinu enuma, svi stari redovi u bazi odjednom znače nešto drugo. Sa STRING u bazi piše 'WAITING' i CHECK constraint radi.
fetch = LAZY na @ManyToOneDefault za @ManyToOne je EAGER — svaki findById(ticket) bi povukao i red, i lokaciju, i uslugu. Lazy povlači tek kad zatreba.
@CreationTimestampHibernate postavlja sam pri insertu. updatable=false da se ne može naknadno promijeniti.
Lombok @Getter @SetterManje šuma. @Data se izbjegava na entitetima jer generiše equals/hashCode nad svim poljima — a to s lazy vezama i ID-om koji je null prije inserta pravi suptilne bugove.

Dirty checking — mehanizam koji treba razumjeti

Entitet učitan unutar @Transactional metode je managed: Hibernate čuva snimak njegovog stanja. Na commitu uporedi trenutno stanje sa snimkom i za svaku razliku pošalje UPDATE — bez ijednog poziva save().

@Transactional
public TicketResponse create(Long queueId, String email) {
    Queue queue = queueService.getEntityForUpdate(queueId);
    queue.setLastNumber(sljedeci);     // ← nema save(); UPDATE ide na commitu

    Ticket ticket = new Ticket();      // NOV objekat, Hibernate ga ne zna
    ...
    Ticket snimljen = repository.save(ticket);   // ← save() OVDJE treba (INSERT)
}
Zamka: bez @Transactional entitet je poslije repozitorija detached — setteri rade u memoriji, ništa ne ode u bazu, i nema greške. Tiho ne radi. Zato je anotacija na svakoj metodi koja mijenja stanje.

Interfejs bez implementacije — Spring je generiše pri startu iz imena metode.

Kako se ime čita:

findFirst  By  QueueId And IssuedDate And Status  OrderBy SequenceNo Asc
   │            │           │            │              │
 LIMIT 1      WHERE queue_id=? AND issued_date=? AND status=?   ORDER BY sequence_no ASC

Riječi između find i By se ignorišu — služe ljudima. Zato findWithLockById radi isto što i findById; lock dodaje anotacija, a ime samo upozorava pozivaoca.

Kad ime nije dovoljno — @Query s JPQL-om ili nativnim SQL-om. U AnalyticsRepository koristimo nativni jer JPQL ne poznaje COUNT(*) FILTER (WHERE …) ni EXTRACT(EPOCH FROM …).

Kad zvati tuđi repozitorij, a kad tuđi servis

Zovi servis kad ti treba tuđe pravilo; zovi repozitorij samo kad ti treba goli podatak bez pravila.

TicketService koristi QueueService.getEntityForUpdate (a ne QueueRepository) jer ta metoda nosi pravilo „red se uzima sa lockom, i to samo unutar transakcije". Zaobilaženje servisa bi tiho uklonilo lock.
Istovremeno koristi UserRepository direktno, jer mu treba samo „nađi korisnika po emailu" — nema pravila koje bi se prekršilo.

7. Servisi i transakcije

Šta je transakcija

Grupa SQL naredbi koju baza tretira kao jednu: BEGIN … COMMIT (sve prođe) ili ROLLBACK (nijedna). create() radi dva upisa (UPDATE queue za brojač i INSERT ticket). Bez transakcije, ako insert padne, brojač je već povećan — red zauvijek preskoči broj.

Kako Spring to izvodi

@Transactional radi kroz proxy: Spring omota bean objektom koji prije metode uradi BEGIN, poslije normalnog return-a COMMIT, a na RuntimeException ROLLBACK. Transakcija je vezana za nit, pa sve što metoda pozove radi u istoj transakciji.

Dvije klasične zamke:
1. Self-invocation: this.drugaMetoda() iz iste klase zaobilazi proxy — anotacija ne važi. Rješenje: izdvojiti u drugi bean.
2. Checked exception ne rollbackuje po defaultu. IOException iz @Transactional metode → commit svejedno prođe. Mijenja se sa rollbackFor = Exception.class.

Dio III — Mehanizmi

10. State machine — životni ciklus ticketa

Problem

Ticket ima sedam stanja. Bez pravila, šalter bi mogao „završiti" ticket koji nikad nije pozvan, ili vratiti otkazani u red. Svaka takva greška je nevidljiva dok statistika ne počne davati besmislice.

Rješenje: tabela dozvoljenih prelaza u enumu

public enum TicketStatus {
    WAITING, CALLED, SERVING, COMPLETED, CANCELLED, NO_SHOW, SKIPPED;

    // Ispod konstanti: Java inicijalizuje enum odozgo - prvo konstante, pa statička polja.
    private static final Map<TicketStatus, Set<TicketStatus>> DOZVOLJENI = Map.of(
            WAITING,   EnumSet.of(CALLED, CANCELLED),
            CALLED,    EnumSet.of(SERVING, NO_SHOW, SKIPPED),
            SERVING,   EnumSet.of(COMPLETED),
            SKIPPED,   EnumSet.of(WAITING),
            COMPLETED, EnumSet.noneOf(TicketStatus.class),   // završno stanje
            CANCELLED, EnumSet.noneOf(TicketStatus.class),
            NO_SHOW,   EnumSet.noneOf(TicketStatus.class));

    public boolean moze(TicketStatus cilj) {
        return DOZVOLJENI.get(this).contains(cilj);
    }
}

Završna stanja moraju biti u mapi s praznim skupom — inače get() vrati null i contains baci NullPointerException.

Jedina tačka gdje se status mijenja

private TicketResponse promijeni(Ticket ticket, TicketStatus cilj) {
    TicketStatus trenutni = ticket.getStatus();

    if (!trenutni.moze(cilj)) {
        throw new InvalidStateTransitionException(
                "Ticket " + ticket.getNumber() + ": prelaz " + trenutni + " -> " + cilj
                        + " nije dozvoljen");                    // -> 409 Conflict
    }

    ticket.setStatus(cilj);

    // Vremenske oznake SAMO pri prvom ulasku u stanje - nose V6 statistiku.
    if (cilj == TicketStatus.CALLED && ticket.getCalledAt() == null) {
        ticket.setCalledAt(OffsetDateTime.now());
    }
    if (cilj == TicketStatus.COMPLETED) {
        ticket.setCompletedAt(OffsetDateTime.now());
    }

    events.objavi(TicketEvent.promijenjen(ticket));
    cache.evictAfterCommit(ticket.getQueue().getId());
    return TicketResponse.from(ticket);        // bez save(): dirty checking
}

Sedam javnih metoda (call, startServing, complete, noShow, skip, requeue, cancel) su jednolinijske — svaka zove promijeni s drugim ciljem.

Zašto mapa, a ne if/else u servisu? Pravilo živi uz podatak koji opisuje. Dodavanje stanja je jedan red u mapi, ne traženje po servisu.
Zašto je promijeni privatna? Da setStatus postoji na tačno jednom mjestu. Nijedan drugi kod — ni kontroler, ni WebSocket, ni Rabbit listener — ne može promijeniti status zaobilazeći provjeru.
Zašto calledAt samo prvi put? Ticket može ići CALLED → SKIPPED → WAITING → CALLED. Vrijeme čekanja se mjeri do prvog poziva; prepisivanje bi statistiku učinilo lažno dobrom.

11. Security: JWT, filter chain, uloge

Dvije faze

LOGIN (jednom):    lozinka --BCrypt.matches--> OK --JwtService.generate--> token
SVAKI ZAHTJEV:     token --JwtAuthFilter--> SecurityContext --chain/@PreAuthorize--> kontroler

BCrypt — lozinke

U bazu ide samo hash ($2a$10$N9qo8uLO..., 60 znakova), nikad lozinka. BCrypt je namjerno spor (cost faktor) i sam dodaje salt — pa ista lozinka dva puta daje različit hash, i rainbow tabele ne pomažu. Provjera nije dešifrovanje (nemoguće) nego ponovno hashiranje i poređenje.

JWT — struktura

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJtYXJrb0B0ZXN0LmNvbSIsInJvbGUiOiJNQU5BR0VSIn0 . 4f2a...
+---- header -----+   +-------------- payload --------------------------+   + potpis +

Prva dva dijela su obični base64 — svako ih može pročitati (zalijepi token na jwt.io). Sigurnost je u potpisu: HMAC-SHA nad prva dva dijela, s tajnim ključem. Promijeniš payload → potpis se ne slaže → token bezvrijedan.

Zato u token nikad ne ide ništa tajno. Samo identitet i ono što smije biti javno. 
public String generate(User user) {

13. Concurrency: race condition i pesimistički lock

Najvažnije poglavlje za intervju. Metoda je bila: prvo dokazati problem testom, pa ga tek onda rješavati.

Problem — dokazan prije popravke

Izdavanje broja je „pročitaj brojač → dodaj 1 → upiši". To nije atomično:

nit A                          nit B
-----                          -----
SELECT lastNumber -> 7
                               SELECT lastNumber -> 7      <- isti broj!
UPDATE lastNumber = 8
INSERT ticket A008
                               UPDATE lastNumber = 8
                               INSERT ticket A008          <- duplikat / constraint puca

Test sa 20 paralelnih niti je pokazao da dvije od tri mušterije dobiju grešku umjesto broja, a pet šaltera pozove samo šest različitih ljudi.

Rješenje: pesimistički lock na redu

// repozitorij: anotacija dodaje "FOR UPDATE" na SELECT
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Queue> findWithLockById(Long id);

// servis: lock vrijedi samo unutar POZIVAOČEVE transakcije
@Transactional(propagation = Propagation.MANDATORY)
public Queue getEntityForUpdate(Long id) {
    return repository.findWithLockById(id)
            .orElseThrow(() -> new NotFoundException("Red " + id + " ne postoji"));
}

Rezultujući SQL: SELECT * FROM queue WHERE id = 1 FOR UPDATE. Postgres zaključa taj jedan red dok transakcija ne završi; druga nit koja traži isti red čeka na samom SELECT-u i onda čita svježu vrijednost.

Tri sloja koja moraju biti zajedno

TicketService.create()          @Transactional       -> otvara transakciju, drži do commita
   +- QueueService.getEntityForUpdate()  MANDATORY   -> ne otvara svoju
        +- QueueRepository.findWithLockById()  @Lock -> SELECT ... FOR UPDATE

Skloni bilo koji i lock ne radi:

  • bez @Lock → običan SELECT → trka
  • sa REQUIRES_NEW umjesto MANDATORY → lock se pušta čim metoda vrati red, prije nego pozivalac upiše → trka
  • bez @Transactional na create → MANDATORY baca grešku odmah (i to je dobro: greška umjesto tihe trke)
Zašto MANDATORY, a ne obični @Transactional? S REQUIRED bi danas radilo isto (pridružio bi se postojećoj transakciji). MANDATORY je ograda za budućnost: ako neko sutra pozove getEntityForUpdate iz metode bez transakcije, REQUIRED bi tiho otvorio kratku transakciju i lock bi bio beskoristan; MANDATORY baca grešku pri prvom pozivu.

Pesimistički vs optimistički — trade-off

Pesimistički (FOR UPDATE)Optimistički (@Version)
Kakozaključaj prije čitanja, ostali čekajučitaj slobodno, na upisu provjeri je li se verzija promijenila; ako jeste — greška, pa retry
Dobro kadsukobi su čestisukobi su rijetki
Cijenaniti čekaju; rizik deadlocka ako se redoslijed zaključavanja razlikujepod opterećenjem mnogo neuspjelih pokušaja i grešaka prema korisniku
Ovdjeizabrano — u špici svi gađaju isti redretry bi vraćao greške mušterijama koje samo hoće broj

Deadlock i kako je izbjegnut

Deadlock nastaje kad nit A drži X i čeka Y, a nit B drži Y i čeka X. Kod nas i create() i callNext() zaključavaju isti red, prvi — dakle uvijek isti redoslijed, pa ciklus nije moguć. Opšte pravilo: ako svi uzimaju lockove u istom redoslijedu, deadlocka nema.

Zašto lock u bazi, a ne synchronized u Javi

synchronized važi unutar jedne JVM. Sa dvije instance backenda (docker compose --scale backend=2) svaka bi imala svoju bravu i trka se vraća. Postgres je jedan i njegov lock važi za sve instance.

Rupa koja ostaje: dual write i outbox pattern

Commit prođe → Rabbit ugašen → događaj izgubljen zauvijek. Ovo je fundamentalan problem: ne postoji način da se atomično upiše u bazu i pošalje u drugi sistem.

Outbox pattern: događaj se upiše u tabelu outbox u istoj transakciji kao i ticket (jedan commit, oba ili nijedno), a poseban proces čita tu tabelu i šalje u Rabbit, brišući poslane. Ako Rabbit padne, red čeka u bazi.

Nije implementiran — svjesna odluka: za ovaj sistem je gubitak jednog SMS-a prihvatljiv, a outbox donosi novu tabelu, scheduler i novi izvor grešaka. Na intervjuu: „šaljem poslije commita, što rješava rollback problem; za garanciju isporuke trebao bi outbox — znam gdje je rupa i svjesno je nisam zatvorio."

Potrošač i ACK

Spring podigne nit po @RabbitListener; Rabbit joj gura poruke (nema pollinga). Za svaku: JSON → objekat → poziv metode → ako metoda završi normalno, pošalje ACK i Rabbit briše poruku. Ako baci — retry, pa DLQ.

Rabbit ne briše poruku kad je pošalje, nego kad primalac potvrdi. Ako backend padne usred obrade, poruka se vrati u queue i isporuči ponovo. Odatle garancija at-least-once — i odatle problem duplikata.

Zašto ista transakcija — dva scenarija

ISTA TRANSAKCIJA (naše):
  marker upisan -> obrada pukne -> ROLLBACK briše I MARKER
  -> Rabbit redostavlja -> guard kaže "nov" -> obrada se ponovi.  ✓ ništa izgubljeno

REQUIRES_NEW (marker u svojoj transakciji):
  marker COMMITOVAN odmah -> obrada pukne -> rollback samo obrade
  -> Rabbit redostavlja -> guard kaže "VEĆ OBRAĐENO" -> preskoči.  ✗ događaj izgubljen zauvijek

Retry i dead letter queue

Tok kad listener baci: pokušaj (1 s) → pokušaj (2 s) → pokušaj → „Retries exhausted" → NACK bez requeue → queue ima x-dead-letter-exchange → poruka ide u ticket.analytics.dlq s headerom x-death.

default-requeue-rejected=false je ključan. Default je true: odbijena poruka se vraća na početak queue-a, listener je odmah opet uzme, opet pukne — beskonačna petlja koja blokira sve poruke iza nje (poison message). DLQ je rješenje: poruka sjedi gdje je čovjek može pogledati, glavni queue teče dalje.

Tri pokušaja su u istoj isporuci, u memoriji backenda (Spring Retry) — Rabbit vidi jednu isporuku i na kraju jedan NACK. Prolazna greška (baza nakratko nedostupna) se sama riješi; trajna ode u DLQ.

Dio V — Intervju

21. Pitanja i odgovori

Arhitektura

Zašto monolit, a ne mikroservisi?

Mikroservisi rješavaju probleme koje ovaj sistem nema — nezavisan deploy timova, različita skaliranja, različiti jezici — a donose distribuirane transakcije, mrežne greške i pet pipeline-a. Napravio sam modularni monolit s čistim granicama po paketima: ako neki modul preraste, izdvaja se. Obrnuto (spajanje prerano rascijepljenih servisa) je mnogo skuplje.

Gdje ide poslovna logika i zašto?

U servis. Kontroler radi HTTP stvari (token, validacija, DTO), repozitorij upite. Konkretan dokaz zašto: u V5 sam dodao RabbitMQ listener koji zove iste servise bez HTTP zahtjeva — da je provjera prelaza stanja bila u kontroleru, taj put bi je zaobišao. Izuzetak je rate limit, koji je namjerno u kontroleru jer je pravilo za HTTP pozivaoca, a ne poslovno pravilo.

Transakcije i concurrency

Šta je race condition i kako si ga riješio?

Izdavanje broja je „pročitaj brojač, dodaj 1, upiši" — dvije niti pročitaju istu vrijednost i obje upišu istu. Prvo sam ga dokazao: test sa 20 paralelnih niti, bez @Transactional na klasi (inače bi sve bilo u jednoj transakciji i trke ne bi bilo), s CountDownLatch da krenu istovremeno. Pale su dvije od tri. Rješenje je pesimistički lock na redu: @Lock(PESSIMISTIC_WRITE) daje SELECT … FOR UPDATE, pa druga nit čeka na SELECT-u dok prva ne commituje.

Zašto pesimistički, a ne optimistički?

Sukobi su ovdje česti — u špici svi gađaju isti red. Optimistički (@Version + retry) je bolji kad su sukobi rijetki; pod ovim opterećenjem bi vraćao greške ljudima koji samo hoće broj. Cijena pesimističkog je da niti čekaju i da postoji rizik deadlocka — koji sam izbjegao time što i create i callNext zaključavaju isti red prvi, dakle uvijek isti redoslijed.

Šta je Propagation.MANDATORY i zašto je tu?

Znači „moram biti pozvan iz već otvorene transakcije, inače greška". Lock živi tačno koliko i transakcija. Da je getEntityForUpdate imao svoju (REQUIRES_NEW), lock bi se pustio čim metoda vrati red — prije nego pozivalac upiše — i trka se vraća. Sa REQUIRED bi danas radilo, ali bi se greška mogla uvući sutra; MANDATORY je ograda koja puca odmah.

Zašto lock u bazi, a ne synchronized?

synchronized važi unutar jedne JVM. Čim pokrenem dvije instance backenda, svaka ima svoju bravu i trka se vraća. Postgres je jedan.

Kada se transakcija rollbackuje?

Na RuntimeException i Error. Checked izuzeci ne rollbackuju po defaultu — to je česta zamka; mijenja se s rollbackFor. Druga zamka je self-invocation: this.metoda() iz iste klase zaobilazi proxy, pa anotacija ne važi.

Keširanje

Koju strategiju keširanja koristiš?

Cache-aside: čitanje puni keš, pisanje ga briše (ne upisuje novu vrijednost). Brisanje ne može biti pogrešno — najgore je jedan dodatni upit. Write-through bi zahtijevao da servis izračuna cijelu novu listu i pravio bi dvije istine.

Zašto brišeš keš poslije commita, a ne @CacheEvict?

Dva razloga. Ključ je queueId, a metode primaju ticketId. I važnije: @CacheEvict briše dok transakcija traje, pa konkurentni čitač u tom prozoru pročita staro stanje iz baze i vrati ga u keš — ekran laže do isteka TTL-a. Registrujem afterCommit callback, i TTL od 30 s držim kao sigurnosnu mrežu.

Šta se desi kad Redis padne?

Aplikacija radi sporije, ne pada i ne visi. CacheErrorHandler logira i pušta poziv u bazu. Ali to nije bilo dovoljno: Lettuce po defaultu čeka 60 s i dok zna da je veza pukla stavlja komande u red — pa sam dodao timeout=1s i REJECT_COMMANDS. I još jedan bug koji sam našao tek gašenjem Redisa: handler štiti samo anotacije, a moj direktan cache.evict() u afterCommit je rušio POST s 500 za ticket koji je već bio u bazi — treba mu svoj try/catch.

Rate limiting

Kako radi token bucket i zašto ne brojač po minuti?

Kanta s N žetona koja se puni N po minuti; zahtjev troši jedan. Brojač po kalendarskoj minuti ima rupu na granici: 5 u 12:00:59 + 5 u 12:01:00 = 10 u sekundi.

Zašto je stanje u Redisu i zašto po korisniku?

U memoriji bi dvije instance backenda dale dupli limit. Po korisniku, a ne po IP-u, jer cijela čekaonica dijeli jedan WiFi — jedan čovjek bi blokirao sve. Endpoint ionako traži token.

Šta ako Redis padne — propuštaš ili blokiraš?

Fail-open, svjesno. Rate limit štiti od zloupotrebe, nije sigurnosna granica; bolje je da ljudi uzimaju brojeve bez limita nego da niko ne može. Za login ili plaćanje bi odluka bila obrnuta.

Poruke

Zašto broker, a ne direktan poziv?

Da šalter ne čeka SMS provajdera, da pad provajdera ne ruši operaciju koja je u bazi uspjela, i da novi potrošač ne traži izmjenu servisa. TicketService ne zna da notifications i analytics postoje.

Kako garantuješ da poruka ne ode za rollbackovan podatak?

objavi() samo publikuje Spring in-process event; slanje je u @TransactionalEventListener(AFTER_COMMIT). Prije commita ništa ne izlazi iz JVM-a.

A ako commit prođe pa Rabbit padne?

Događaj je izgubljen — logujem ERROR. To je dual write problem i rješava ga outbox pattern: događaj se upiše u tabelu u istoj transakciji, poseban proces ga šalje. Nisam ga implementirao; za ovaj sistem je gubitak jednog SMS-a prihvatljiv, a outbox donosi tabelu, scheduler i nove greške. Znam gdje je rupa.

Šta je at-least-once i kako se braniš od duplikata?

Rabbit briše poruku tek na ACK; ako potrošač padne poslije obrade a prije ACK-a, poruka se redostavlja. Svaki događaj nosi UUID, a potrošač prije obrade upiše (consumer, eventId) u processed_event. Ključno: marker i obrada su u istoj transakciji — ako obrada pukne, rollback briše i marker, pa se redostava obradi kao prva. Sa REQUIRES_NEW bi marker ostao i događaj bi bio izgubljen zauvijek. Dodatno, UNIQUE(event_id) u tabeli je drugi sloj.

Šta je DLQ i zašto requeue=false?

Poruka koju listener ne može obraditi bi se s requeue=true vraćala na početak queue-a u beskonačnoj petlji i blokirala sve iza sebe — poison message. Sa false i deadLetterExchange, poslije 3 pokušaja s backoffom ide u <ime>.dlq gdje je čovjek pregleda.

Zašto topic exchange i dva queue-a?

Topic dozvoljava da se potrošač pretplati šablonom — novi potrošač koji hoće samo ticket.called ne traži izmjenu producera. Dva queue-a jer bi jedan zajednički dijelio poruke između potrošača; ovako svaki dobije svoju kopiju, i pad jednog ne utiče na drugog.

Security

Objasni tok autentikacije.

Login: BCrypt matches nad hashom iz baze, pa JwtService.generate. Svaki sljedeći zahtjev: JwtAuthFilter pročita Authorization header, provjeri potpis i rok, učita korisnika iz baze (da promjena uloge odmah važi) i upiše Authentication u SecurityContext — ThreadLocal vezan za tu nit. Zatim filter chain provjerava URL pravila, a @PreAuthorize ulogu.

401 ili 403?

401 „nisi se predstavio", 403 „predstavio si se, nemaš prava". Springov default entry point vraća 403 pa sam ga zamijenio. I naletio sam na zamku: kad @PreAuthorize odbije, Spring interno šalje zahtjev na /error, koji opet prolazi kroz lanac s praznim kontekstom — bez /error kao permitAll, 403 bude pregažen sa 401.

Zašto je CSRF isključen?

CSRF brani od zloupotrebe kredencijala koje browser šalje sam — prvenstveno cookie-ja. Token je u Authorization headeru koji browser ne prilaže automatski, pa napad ne postoji. Da koristim cookie za token, CSRF bi morao ostati.

Može li se JWT poništiti?

Ne u ovoj postavci — server ga ne pamti, pa vrijedi do isteka. Rješenja su blacklista u Redisu ili kratki access token + refresh token. Za ovaj sistem sam izabrao rok od 2 h i prihvatio ograničenje.

Testiranje i infrastruktura

Zašto Testcontainers, a ne H2?

Zato što kod koristi stvari koje H2 nema ili radi drugačije: COUNT(*) FILTER, EXTRACT(EPOCH …), SELECT … FOR UPDATE, timestamptz. Test koji prolazi na H2 a pada u produkciji daje lažnu sigurnost.

Kako se testira concurrency?

ExecutorService + CountDownLatch da niti krenu istovremeno, ConcurrentLinkedQueue za rezultate, i bez @Transactional na klasi. Prvo sam napisao test koji pada, pa dodao lock — dokaz prije popravke.

Šta radi multi-stage build?

Prva faza ima Maven i JDK i pravi jar; druga kreće od praznog JRE image-a i uzima samo jar. Rezultat je ~200 MB umjesto ~800 MB, bez kompajlera i izvornog koda u produkciji. Sloj iz prethodne faze se ne može obrisati — može se samo ne uzeti.
